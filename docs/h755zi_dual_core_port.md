# H755ZI dual-core port notes

## Scope

This branch ports the later sensor-runtime work onto the STM32H755ZI CM7 tree:

- IMU runtime request arbitration and snapshot publishing
- Power runtime snapshot publishing
- Manual validation command parser and actuator override path
- H7 timer/NVIC setup for the 1 kHz control ISR

The runtime remains on Cortex-M7. Cortex-M4 is still generated by CubeMX but has no project application ownership in this port.

## Board and MCU delta

Previous firmware target:

- Board: NUCLEO-L476RG / STM32 Nucleo-64
- MCU: STM32L476RG, single Cortex-M4
- Max MCU frequency from ST product docs: 80 MHz
- Package in the old `.ioc`: LQFP64
- Old project clock in `.ioc`: `SYSCLK=16 MHz`, `HCLK=16 MHz`

New firmware target:

- Board: NUCLEO-H755ZI-Q / STM32H7 Nucleo-144
- MCU: STM32H755ZI, dual Cortex-M7 plus Cortex-M4
- Max MCU frequency from ST product docs: Cortex-M7 up to 480 MHz, Cortex-M4 up to 240 MHz
- Package in the H7 `.ioc`: LQFP144
- Current project clock in `.ioc`: `CpuClock=64 MHz`, `CortexFreq=64 MHz`, `CPU2Freq=64 MHz`, `HCLK=64 MHz`

Do not assume the project is running the H755ZI at its maximum rated frequency. The current generated clock tree is intentionally recorded as 64 MHz until CubeMX/CubeIDE clock configuration is changed and regenerated.

## Dual-core boot notes

The STM32CubeH7 dual-core examples use CM7 as CPU1 for system init, system clock, voltage scaling, and optional release of CM4 through HSEM/domain wakeup. Keep this port conservative:

- CM7 owns ADCS, IMU, power sampling, manual validation, UART logging, and TIM6 control tick.
- CM4 remains generated but idle until there is a clear task split and a tested inter-core communication path.
- If CM4 is later used, verify option bytes and startup sequence before moving peripherals. ST examples commonly gate CM4 and let CM7 release it after system init.

## Pin and peripheral mapping

The logical peripheral mapping is retained from the old branch and translated to the H755ZI package in `cube_sat_nucleo.ioc`.

| Function | H755ZI signal | Notes |
| --- | --- | --- |
| USART2 TX/RX | PA2 / PA3 | UART console, logging, and HITL packet compatibility |
| TIM2 PWM CH1/CH2 | PA0 / PA1 | Magnetorquer PWM outputs |
| TIM6 | internal | 1 kHz control ISR |
| I2C1 SCL/SDA | PB8 / PB9 | INA219 current sensor |
| I2C2 SCL/SDA | PB10 / PB11 | ADT7420 temperature sensor |
| SPI3 SCK/MISO/MOSI | PC10 / PC11 / PC12 | BNO085 IMU |
| IMU CS | PB2 | GPIO output, active low |
| IMU RST | PB5 | GPIO output |
| IMU INT | PA10 | GPIO input, pull-up |
| MTQ sleep/fault | PA4 / PA5 | GPIO output/input |

Because Nucleo-64 and Nucleo-144 headers are physically different, verify the actual bench wiring against UM2408/schematics before flight or hardware-in-loop tests. The code preserves logical MCU pins; it does not prove the same jumper/header positions are used.

## Timing and frequency

Old STM32L476 configuration:

- Timer clock: 16 MHz
- TIM2/TIM6 prescaler: 15
- TIM2/TIM6 period: 999
- Frequency: `16,000,000 / (15 + 1) / (999 + 1) = 1,000 Hz`

Current STM32H755 configuration:

- Timer clock from `.ioc`: `RCC.Tim2OutputFreq_Value=64000000`
- TIM2/TIM6 prescaler: 63
- TIM2/TIM6 period: 999
- Frequency: `64,000,000 / (63 + 1) / (999 + 1) = 1,000 Hz`

This keeps:

- Inner loop/control ISR period: 1 ms
- PWM period: 1 ms
- PWM resolution after prescale: 1 us per counter tick

Related runtime periods:

- ADCS task: 10 ms / 100 Hz
- IMU service task: 2 ms / 500 Hz service budget, BNO085 reports requested at 50,000 us / 20 Hz
- Power sample task: `SENSOR_SAMPLE_PERIOD_MS=10 ms`
- Telemetry/log task: 50 ms, consolidated sensor log every 100 ms
- Manual validation task: 10 ms, only owns actuator targets when armed
